1. 문제 정의와 시스템 범위

한국환경공단은 환경기초시설(소각·하수처리·바이오 등) 의 관급자재(펌프·송풍기·약품·계측기 등)를 조달하면서, 정부의 사회적 가치 정책에 따라 일정 비율 이상 SR(중소·여성·장애인·사회적기업 등)을 충족해야 한다. 같은 세부품명번호를 공급할 수 있는 사업자등록번호(BRN) 가 수십~수백 곳에 달해, 어떤 공급자 풀이 충분하고 신뢰 가능한지를 발주 담당자가 직관만으로 판단하기 어려운 구조다.

본 시스템은 발주 담당자가 단시간 내에 후보 BRN을 비교하고 결정할 수 있도록 돕는 의사결정 지원 도구로 정의한다. 자동 발주가 아닌 의사결정 보조 도구이며, 이 전제에 따라 운영 범위를 다음과 같이 제한한다.

  • 예측이 아닌 후보 제시: ML 모델이 "이 BRN이 낙찰자다"라고 단언하지 않는다. 사용자가 비교할 수 있는 상위 K개 후보와 근거를 제공한다.
  • 원점수 확률 비공개: 보정(calibration) 이 보장되지 않은 ML 출력 확률을 사용자에게 노출하지 않는다. 등급(A/B/C) 또는 순위만 사용한다.
  • 권한·책임 분리: 사용자에게 데이터 적재 실행 권한을 부여하지 않는다. 데이터 최신성 관리는 운영팀이 담당한다.
  • 정책 요건과 시장 신호의 분리: SR 의무비율은 점수 산출 규칙에 반영하고, 시장 변수는 ML 모델이 학습하도록 점수 산출 로직과 학습 모델의 역할을 분리한다(§8 참조).

분석의 최소 단위(PK)는 세부품명번호(10자리) × 사업자등록번호(BRN, 10자리) 다. 모든 데이터셋이 이 두 키로 join된다.

4.3 등급(Tier)

최종 점수 분포에 따라 A (우선 추천) / B (추천) / C (검토) 로 분류한다. 컷오프는 TIER_A_CUTOFF = 0.6, TIER_B_CUTOFF = 0.3 (pipeline/recommend_v2.py L107-108). 단, 리스크 등급이 "주의" 이면 점수와 무관하게 C 로 강등한다 (_tier() L435-442). 원점수 자체는 카드 우측에 보조 표시한다 (rule_score 0.73 형태). 보정(calibration) 이 없으므로 "점수 0.73 = 낙찰 확률 73%" 같은 해석은 성립하지 않는다.

5. 가중치·보정 값의 근거

모든 숫자는 휴리스틱이다. 데이터로 학습하거나 calibration 을 수행한 부분은 없다. 다만 각 결정은 다음 의도를 따른다.

대상설계 의도
SR 을 점수에서 분리 SR 인증은 본질적으로 이진 상태다 — 보유하거나 보유하지 않거나. 연속 점수 (0.35 × sr) 로 다른 축과 합산하면 "SR 미보유지만 실적이 강한 BRN" 이 SR 보유자보다 상위로 올라올 수 있어, 정책 의무비율 충족 여부가 가중치 magnitude 와 다른 축 분포에 의존한다. 이전 구현은 그래서 SR floor demote (−1.0) 를 추가로 얹어 강제 강등했다 — 결국 가중치는 0.35 였지만 실제로는 hard 필터처럼 동작했다. 명시적으로 분리하는 편이 정직하다. 토글 ON = SR 보유 BRN 만 풀에 진입 (sr_only bool), OFF = 전체. 정책 충족 책임은 토글 사용자 (공무원) 에게 명시적으로 넘긴다.
가중치 거의 균등 (track 0.33 / price 0.34 / supply 0.33) SR 이 빠진 뒤 남은 3축에 대한 도메인 합의가 없다. "실적이 가격보다 중요한가" 같은 질문에 답할 학습 라벨이 없으므로 균등 배분이 default 다. 0.33 / 0.34 / 0.33 합 = 1.00 (_validate_weights 검사 통과).
가격 0.34 — 동점 시 tiebreak 3축 중 가격만 미세하게 +0.01 높다. 점수가 묶일 때 가격경쟁력이 높은 BRN 을 우선시한다는 약한 신호. 발주 의사결정에서 가격이 가장 즉시적 효용이라는 도메인 직관 외 근거는 없다.
ComplianceBar 유지 스코어링과 별도로 상위 K 결과 카드의 SR 보유 비율을 게이지로 보여준다 (ComplianceInfo.sr_pct_top_k vs obligation_threshold_pct). 점수가 SR 을 반영하지 않으므로 사용자가 의무비율 충족 여부를 한 눈에 확인할 수 있어야 한다. 미충족 시 토글을 켜거나 K 를 늘리는 운영 액션을 유도한다.

SR 점수 반영 vs 토글 필터 비교

접근장점단점
SR 점수 반영 + floor demote (이전) 의무비율을 추천 결과가 자동 충족하는 경향 가중치 0.35 와 demote −1.0 두 knob 이 동시에 작용해 어느 쪽이 정렬을 결정하는지 불투명. SR 보유자가 풀에 3명 미만이면 demote 미발동으로 동작이 갑자기 바뀜.

축 상관 (재확인)

실적축의 norm_count 항과 공급축이 동일 변수 award_count 를 본다 (§4.1 callout). 가중 0.33 + 0.33 = 0.66 이 한 신호에 묶임. SR 이 빠지면서 이 상관 비율이 4축 시절 0.45 보다 두드러진다. 풀 내 활동량이 많은 BRN 이 두 축에서 동시에 점수를 가져가므로, 추천 결과가 실적 중심으로 쏠리는 경향이 강해진다.

검증 한계

  • 운영 피드백 라벨 (좋은 추천 / 나쁜 추천) 이 수집되지 않아 가중치 학습은 불가능하다.
  • A/B 테스트는 수행되지 않았다.
  • 0.33 / 0.34 / 0.33 라는 균등 배분 자체에 통계적 근거는 없다. 현재 정당화는 "도메인 합의 부재 시 균등이 가장 안전한 default" 다.
  • SR 을 점수에서 뺀 결정 자체도 운영 검증 전이다 — 토글을 끄고 쓰는 사용자가 정책 의무비율을 챙기지 못하는 시나리오가 실제로 얼마나 발생하는지는 운영 로그가 쌓여야 보인다.
  • 운영 단계 진입 후 사용자 클릭/선택 + 토글 사용 로그를 수집하면 메타-ranker (가중치 학습) 와 SR 토글 default 정책을 데이터로 결정할 수 있다 (§10).

6.3 운영에 도움이 안 된 세 가지 사유

  1. 의사결정 단위와 군집 단위의 불일치 — 추천은 "1 발주 × N 후보" 단위로 일어나는데, 군집은 전체 풀을 한 번 자른 정적 라벨이다. Stage 1 keyword retrieve로 풀이 좁아진 시점에서 군집 정보의 의사결정 기여도가 낮아진다.
  2. 이미 도메인 코드로 가능한 분류 — prefix4 + dormant_months + real_sr_flag 세 컬럼이면 군집 라벨과 거의 같은 정보가 나온다. 별도 군집 enum을 두면 한국어 라벨에 의존한 분기(Hyrum's Law) 위험까지 추가된다. 라벨 문구가 변경되면 의도하지 않은 분기 오류가 발생할 수 있다.
  3. 데이터 규모 한계 — 활성 BRN 1,694명, 학습 positive 449건은 UMAP+HDBSCAN의 안정성을 보장하기에 충분하지 않을 수 있다. 재학습마다 군집 ID가 흔들릴 위험이 있으며 (안정성 정량 검증 미수행), 운영 일관성 보장이 어려우므로 보수적으로 운영 경로에서 제외한다. 사용자에게 "이번 주의 cluster 1" 과 "지난주의 cluster 1" 의 의미를 일관되게 설명할 수 없는 상황을 피한다.

결과적으로 운영 카드 표층에서 cluster_label을 제거했고, 가중치 보정에서도 클러스터 신호를 제거했다. 코드 자산(pipeline/clustering.py, artifacts/clustering_*) 은 archival 목적으로 보존하되 운영 경로에서는 분리한다.

운영상 시사점: 정량 지표(Silhouette, DBI) 가 양호해도 새로운 도메인 의미가 도출되지 않으면 운영 의사결정에 추가 기여가 제한적이다. 비지도 학습은 "발견" 도구가 아니라 기존 분류의 "검증" 도구로 위치하는 편이 적합하다.

해석 — 시장 변수와 정책 의무 변수의 분리:
실제 낙찰을 결정하는 것은 BRN 이력, 품목 적합도, 시기 같은 시장 변수다. SR 인증은 정책 의무 충족 여부를 보장하는 별도 차원이다. Classifier가 SR 4피처에 0 importance를 부여한 것은 도메인 사실의 반영으로 해석할 수 있다. Ranker가 작은 importance(77~189) 를 부여한 것은 group 내 동률 후보를 가르는 tie-break 신호로 사용했기 때문이다.

단, importance=0 은 SR 정보가 다른 피처 (g2b_age_years, corp_size 등) 에 간접 인코딩되어 트리 분할 선택을 받지 못했을 가능성도 있다. 두 가설 중 어느 쪽이든 운영 결론(SR 은 룰로 강제) 은 동일하다.

운영적 함의: SR 다양성은 모델이 학습하는 것이 아니라 운영 층에서 분리해 다루는 것이 옳다. 현재 설계는 룰베이스 3축(실적 0.33 / 가격 0.34 / 공급 0.33) + SR 토글 필터 + ComplianceBar 게이지 — 점수·풀 진입·정책 게이지 세 면이 명확히 분리된다. ML이 시장을 설명하고, 룰은 후보 정렬, SR 은 풀 자체를 가르는 토글로 책임이 나뉜다 — importance=0 은 SR 정보가 점수 산식 안에 있어야 할 신호가 아니라는 점을 뒷받침한다.

8.5 운영 적용 가능성

8.5.1 사전탐색 모드 미사용 사유

두 모델 모두 (공고, BRN) 쌍 단위로 학습됨. 사전탐색 모드는 공고가 없으므로 공고 측 피처(bid_dtil_prdct_no, presmpt_prce, asign_bdgt_amt, cntrct_cncls_mthd_nm, bid_dminstt_cd) 를 구성할 수 없다. 임의 생성(synthesize) 한 값을 입력하면 학습 분포 밖이 되어 예측 신뢰도가 낮아진다.

8.5.2 Phase 2 "공고-후 추천 모드" 의 교체 지점

공고가 게시된 직후 후보 BRN 풀을 정렬하는 시나리오에서는 Ranker가 직접 적합:

  • HR@5 0.77 / HR@10 0.92 → 운영 기대치 충족
  • Phase 2 카드 UX: 기본 K=5 노출 + "추가 5건 펼침" 버튼 (HR@10 0.92 활용)
  • RecommendationV2Item.ml_score 필드 이미 자리 잡힘 (인터페이스 한 줄 swap)
  • pipeline.ranker.Ranker Protocol 인터페이스 보존
"한 줄 교체" 의 한계: 인터페이스 교체와 운영 가능성은 다른 차원이다. 공고 측 피처 6개 (bid_dtil_prdct_no, presmpt_prce, asign_bdgt_amt, cntrct_cncls_mthd_nm, bid_dminstt_cd, bid_month) 의 임의 생성, PIT 피처 재계산, 보정(calibration) 등 사전 조건이 충족되어야 실제 운영이 가능하다. 인터페이스 교체 자체는 분 단위지만 사전 조건은 별도 작업이다.

8.5.3 원점수 확률(raw probability) 노출 금지

Classifier scale_pos_weight=154 → 출력 sigmoid 값의 사전 확률이 가중치에 의해 왜곡될 수 있다. "BRN 낙찰 확률 = 0.87" 같은 해석은 성립하지 않는다.
Ranker lambdarank score → 절대 단위 정의 없음. 순위 점수일 뿐.

따라서 두 모델 모두 등급(A/B/C) 또는 순위로만 제시 (CLAUDE.md §9 와 일관).

  • 환경공단 발주 빈도: 일 1.5건 (4개년 평균). 주 누락 ≈ 10건.
